A (Quang) — Làm Playwright / GUI như thế nào

Mục tiêu: lớp hiểu GUI testing và thấy 3 demo chạy được trên EShop (localhost:5173).

Chuẩn bị (tuần đầu)

  1. Chạy EShop trên máy. Làm theo setup_guide.md của SUT; đăng nhập thử test@eshop.com / Test1234!. Chụp ảnh Evidence: trang chạy được.
  2. Xác nhận lỗi GUI thật (dùng làm ví dụ xuyên suốt slide):
    • Giỏ: “Tổng tạm tính” thay vì “Tổng cộng”; xóa không có dialog; thiếu +/-
    • Nút tích cực xanh lá (đặc tả: xanh dương); thiếu đúng 1 <h1>
    • Ô tổng tiền Checkout sửa được; header thiếu badge / highlight
    Chụp ảnh từng lỗi vào Evidence/.
  3. Tạo repo nhóm (nếu chưa có): folder tests/, README ngắn cách chạy EShop + Playwright. Mời B và C vào repo.

Ba demo (làm lần lượt, quay clip từng cái)

  1. Demo 1 — Cài đặt.
    • npm init playwright@latest trong project test
    • Cài @axe-core/playwright
    • Chạy test mẫu → mở HTML report → quay màn hình các bước này
  2. Demo 2 — Cơ bản (Record & Playback + Checkpoint).
    • npx playwright codegen http://localhost:5173
    • Ghi: vào trang → thêm sản phẩm vào giỏ → mở giỏ
    • Sửa file sinh ra: thêm expect kiểm tra nhãn “Tổng cộng” (sẽ fail đúng vì EShop đang ghi “Tổng tạm tính” — đó là điểm dạy)
    • Nhắc trên clip: đây là checkpoint GUI, không assert “giảm giá đúng 10%” (cái đó thuộc T2)
  3. Demo 3 — Luồng phức tạp (Data-driven + visual + a11y).
    • Tạo data/pages.json: home, cart, checkout, login…
    • 3 viewport: mobile 375, tablet 768, desktop 1440
    • Mỗi trang × viewport: toHaveCount(1) cho h1; ảnh có alt; toHaveScreenshot; axe WCAG 2 A/AA trên Checkout
    • Ghi rõ trong báo cáo: Record & Playback / Data-driven / Checkpoints nằm ở demo nào
2 bẫy của EShop khi viết test: (1) Giỏ hàng chỉ lưu trong React state (CartContext.jsx) nên page.goto('/cart') luôn ra giỏ trống — trang cần trạng thái phải tự thêm sản phẩm qua UI trước (thêm trường setup trong pages.json). (2) Nút “Thêm vào giỏ” phải bấm 2 lần mới ăn — đây cũng là một lỗi GUI, ghi vào Evidence. Phần lớn test sẽ fail — đó là kết quả mong muốn; dùng expect.soft để một lần chạy liệt kê đủ vi phạm.
Ranh giới T1 vs T2: click/điền form chỉ để đưa UI về đúng trạng thái. Checkpoint phải là thuộc tính giao diện (toHaveCSS, toHaveAttribute, screenshot, axe) — không kiểm tra nghiệp vụ.

Lý thuyết + bài tập lớp

  1. Viết phần lý thuyết GUI (outline mục 2 proposal): định nghĩa, checklist control, lỗi hay gặp, visual regression, a11y, khi nào nên tự động / thủ công. Gửi C để ghép slide.
  2. Soạn Bài tập 1: “Viết 1 test Playwright kiểm tra 1 yêu cầu FR-21 (vd. mỗi trang đúng 1 <h1>)” + gợi ý 3–5 dòng + đáp án mẫu (không phát đáp án cho lớp trước buổi).

Checklist 50 câu (A phụ trách chính)

  1. Chạy đủ 50 câu trên luồng Checkout EShop (Home → Product → Cart → Checkout, thêm Login/Quên mật khẩu nếu câu hỏi cần). Ghi vào bảng checklist/checklist-50.md (hoặc .csv):
    • Cột: # · Câu hỏi · Nhóm control · Trang · Pass / Fail / N/A · Ảnh Evidence · Ánh xạ FR-21…24 / heuristic
    • Mỗi câu Fail phải có ảnh chụp trong Evidence/checklist/
  2. Phân loại từng câu: Tự động (Playwright/axe kiểm được) · Bán tự động · Bắt buộc thủ công. Những câu “Tự động” đưa vào rules.json / pages.json của Demo 3 → slide có số liệu cụ thể (vd. “tự động được X/50 câu”).
  3. Câu nào thiên về usability (người dùng có hiểu, có biết đang ở bước nào…) thì hỏi B cùng chấm. Lỗi Fail mới phát hiện → bổ sung vào danh sách lỗi đáp án (ground truth) để C dùng chấm AI.
  4. Viết phần slide “Áp dụng checklist trên EShop” (đặt ngay sau lý thuyết GUI): tổng kết Pass/Fail + 3–4 lỗi đắt giá nhất; bảng đầy đủ để ở phụ lục báo cáo. Soạn bản rút gọn kèm đáp án để C đưa vào bài tập/homework.

Done khi có

  • 3 clip YouTube (demo 1–3) + link gửi C
  • Code test trong repo, README chạy được trên máy khác
  • Text lý thuyết GUI + worksheet bài 1
  • Bảng checklist 50 câu (Pass/Fail + Evidence + phân loại tự động/thủ công)
  • Ảnh Evidence lỗi GUI

B (Phúc) — Làm Maze / Usability như thế nào

Mục tiêu: có study thật với ~5 người ngoài nhóm; lớp hiểu metric và xem được heatmap / kết quả.

Chuẩn bị (làm sớm — phụ thuộc URL public)

  1. Deploy EShop ra URL public (trách nhiệm chính của B — làm đầu tiên, Maze và phần so sánh đều chờ việc này).
    • Sửa trước khi deploy: frontend-web đang gọi cứng http://localhost:3000 ở 13 chỗ (AuthContext.jsx, Checkout.jsx, Home.jsx, ProductDetail.jsx, ForgotPassword.jsx, Profile.jsx…). Nếu không sửa, máy người tham gia sẽ gọi vào localhost của chính họ → trang trắng. Đổi thành import.meta.env.VITE_API_URL và đặt biến này = URL backend public. Làm trên branch riêng, không đụng code lỗi GUI.
    • Frontend: Vercel; backend (Express + SQLite): Render / Railway. Lưu ý gói free có thể “ngủ” khi không dùng và file SQLite có thể bị reset khi redeploy → mở trang “đánh thức” server trước mỗi đợt test
    • Hoặc tạm: Cloudflare Tunnel / ngrok cho cả frontend lẫn backend — đủ cho demo, nhưng máy phải bật suốt thời gian người tham gia làm
    • EShop cố ý có lỗ hổng bảo mật: chỉ mở URL trong khung giờ test, chỉ dùng dữ liệu giả
    • Kiểm tra: mở URL trên điện thoại (4G, không cùng wifi), đăng nhập, thêm giỏ, áp mã, đặt hàng được
    • Gửi URL cho cả nhóm; chụp Evidence
  2. Chuẩn bị dữ liệu cho study.
    • DB chỉ có sẵn 1 tài khoản user (test@eshop.com) → thêm 5–6 tài khoản riêng (vd. p1@eshop.com … p6@eshop.com) vào phần seed của backend/database.js. Mỗi người tham gia một tài khoản, gửi kèm link study
    • Dùng mã VIP100 (giảm cố định 100.000₫, đơn tối thiểu 300.000₫, tối đa 2 lần/tài khoản). Không dùng SAVE10: công thức giảm % ở backend đang lỗi, sẽ làm nhiễu kết quả usability
    • Reset DB (node database.js) trước mỗi đợt test
  3. Tạo tài khoản Maze Free. Xác nhận còn Website / Live website test. Nhớ: Free chỉ 1 study/tháng → thiết kế xong trên giấy rồi mới tạo study thật.
    • Đưa bản thiết kế study (mission, câu SEQ, SUS, expected path) cho A và C duyệt trước khi tạo
    • Kiểm chứng trên Maze Help: thao tác trong cùng một trang (bấm “Áp dụng” coupon) có đo thành bước riêng được không
    • Chạy thử (pilot) 1 lượt với một thành viên nhóm trên URL public — chỉ để bắt lỗi kỹ thuật, không tính vào kết quả
  4. Tuyển ~5 người tham gia ngoài nhóm (bạn, SV lớp khác). Không dùng thành viên nhóm (đã biết website). Xin đồng ý nếu có ghi hình / moderated bổ sung.

Ba demo

  1. Demo 1 — Cài đặt. Tạo project Maze → gắn snippet vào index.html (hoặc theo hướng dẫn Maze) trên bản deploy → quay clip các bước + mở URL đã gắn.
  2. Demo 2 — Cơ bản. 1 mission đơn giản + câu SEQ (1–7: dễ hay khó). Tự làm thử 1 lượt → xem path, thời gian, checkpoint trang đích. Clip: tạo mission → làm → đọc kết quả.
  3. Demo 3 — Study Checkout đầy đủ.
    • Mission: “Bạn có 5.000.000₫ và muốn mua một món phụ kiện cho máy tính. Hãy mua một sản phẩm và dùng mã giảm giá VIP100 khi thanh toán.” (Phụ kiện có AirPods 6.000.000₫ và bàn phím Keychron 4.000.000₫ → chỉ bàn phím vừa ngân sách; người dùng phải tự so giá. Không ghi tên nút trong mission.)
    • Sau mission: SEQ — “Nhiệm vụ này dễ hay khó? (1–7)”
    • Thành công = xác nhận đơn ở trang Thanh toán (đặt expected path / URL đích rõ)
    • Cuối study: bảng SUS 10 câu
    • Phân tích: task success, time on task, misclick, heatmap, gợi ý Maze AI (nếu Free có)
    • Ghi trong báo cáo: Record (Maze ghi path) / Data-driven (nhiều người) / Checkpoint (trang đích)
Hạn chế Maze cần nói trên slide: Free 1 study/tháng; bước cùng một trang (vd. bấm “Áp dụng” coupon) Maze có thể không tính là bước vì chỉ theo dõi khi URL đổi; unmoderated thì không hỏi lại được vì sao bị kẹt.

Lý thuyết + bài tập

  1. Viết lý thuyết Usability: ISO 9241-11; Rubin; Nielsen H1–H10 + severity 0–4; moderated/unmoderated; think-aloud; metrics (success, time, error/misclick, SUS, SEQ); test plan 9 phần. Gửi C ghép slide.
  2. Soạn Bài tập 3: làm 1 mission (link study hoặc hướng dẫn tạo) + điền bảng SUS; kèm gợi ý ngắn.
  3. (Tuỳ thời gian) 1–2 buổi moderated ngắn qua Meet để có think-aloud — dùng đúng mission Maze.

Done khi có

  • URL EShop public ổn định (đã bỏ localhost cứng) + 5–6 tài khoản người tham gia + 3 clip Maze
  • Kết quả study ~5 người (ảnh dashboard / export) trong Evidence
  • Text lý thuyết Usability + worksheet bài 3
  • Danh sách participant (ẩn thông tin nhạy cảm nếu cần)

C (Quân) — Làm AI Reviewer & đóng gói như thế nào

Mục tiêu: có script AI chạy được; có số liệu người vs AI; slide/báo cáo/homework ghép đủ để nộp.

Chuẩn bị

  1. Tạo GitHub Projects board: To do / Doing / Review / Done. Mỗi task gắn người + deadline. Nhắc A/B cập nhật hàng tuần; lưu biên bản họp ngắn vào repo.
  2. Chạy được Playwright (xin A hướng dẫn) và mở được study Maze của B — để tự demo được cả bộ khi cần.
  3. Chọn API LLM có vision (Claude hoặc GPT). Giữ key ngoài repo (.env + .gitignore).

Xây AI Heuristic Reviewer

  1. Script Node.js (theo proposal mục 5):
    • Đọc config.json: danh sách URL / bước trên EShop
    • Playwright chụp màn hình từng bước
    • Gửi ảnh + prompt cố định (10 heuristic Nielsen) → JSON theo schema → xuất Markdown
    • Đổi config là chạy được website khác (điểm “tái sử dụng”)
  2. Prompt cần ép: chỉ báo vấn đề nhìn thấy trên ảnh; có heuristic, severity 0–4, evidence, fix. Ví dụ kỳ vọng Giỏ hàng: H3 — xóa không xác nhận, severity 3.
  3. So sánh người vs AI (nội dung chính phần điểm yếu AI):
    • Cùng một bộ ảnh Checkout
    • Cả nhóm đánh giá heuristic thủ công độc lập trước
    • Chạy AI riêng → đếm: trùng / chỉ người / chỉ AI / false positive / lệch severity
    • Kỳ vọng nói trên slide: AI mạnh lỗi bề mặt; yếu lỗi phụ thuộc nghiệp vụ; severity hay lệch
  4. Quay 1 clip AI: chạy script → mở báo cáo → chỉ 1–2 chỗ AI đúng và 1 chỗ AI sai/bịa.
AI Disclosure: mọi đoạn AI viết (slide, báo cáo, prompt output) nhóm review lại và ghi vào form disclosure. Không nộp raw output chưa đọc.

Đóng gói sản phẩm + bài tập

  1. Soạn Bài tập 2 — Heuristic Showdown: ảnh Checkout + yêu cầu tìm ≥5 vi phạm heuristic, rồi so với báo cáo AI (cung cấp sau hoặc tách answer key).
  2. Ghép slide (nền trắng, chữ đen, chữ to): nhận text từ A/B + phần AI của mình; mỗi demo có link YouTube. Format thống nhất trước khi nhồi nội dung.
  3. Ghép báo cáo: mục lục theo proposal; chèn bảng so sánh tool (cả nhóm góp); mục AI + bảng người vs AI; phân công + timeline; tham chiếu.
  4. Thu homework: bản rút gọn Checklist 50 câu do A soạn (đáp án + cách chấm) + 3 bài nhỏ có gợi ý từ A/B/C.

Done khi có

  • Repo: script Reviewer + config.json mẫu + README chạy
  • 1 clip AI + bảng số liệu người vs AI
  • Slide + báo cáo bản ghép (≥90% trước W06)
  • Task board có lịch sử; AI Disclosure điền đủ
